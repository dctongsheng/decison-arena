# Snake 真实轨迹审计：输入、实时延迟与死亡窗口

审计日期：2026-10-17。源码基线 HEAD `7fcba72`，本轮已有工作区变更保留；本审计不修改正式游戏、调度、provider 或数据库代码，不调用真实模型。

## 结论

4 个自然死亡样本均出现「边界前的转向答案晚于死亡」；最新 StartLux 样本在最后一次观察时只剩约 583 ms 撞墙，左转响应耗时 713 ms。**有真实证据支持实时延迟和过时局面是死亡链条的一部分；没有发现动作被执行成别的方向、输入遗漏或旧的“同 tick 未消费就再次观察”调度故障。**

最新 StartLux 样本还证明了请求期间食物已经被吃掉并换位：请求依据旧食物继续向上，接着才观察到新食物。重复 `queued` 的方向很常见，但仅靠动作轨迹不能断言模型误解了 `queued`、100 ms 或坐标。

## 数据边界与重建方法

- 数据只来自本仓库 `.wrangler/state/v3/do` 与 `.wrangler/cloudflare-dev/state/v3/do` 的 `ArcadeSessionObject` SQLite，连接使用 `mode=ro`。只查询记录中的游戏种类、版本、seed（仅内存用于重建）、游戏 state、纯游戏 frames，以及显式白名单的动作/tick/耗时字段。未读取密钥、鉴权 session、账户/凭证表、原始请求或 reasoning 正文；报告不包含完整回放或 seed。
- 先核对 `artifacts/arcade-live-results.json` / `arcade-fix-live-results.json` 等已有摘要；这些较早记录属于 v1。下面只重建 `snake-realtime-v2`、`decision-arena-arcade-v4`，不把 v1 的历史速度套入 v2。
- 使用当前实际 TypeScript `snake` adapter，从原 seed 创建初态；逐 tick `step()`，在原 `input` 事件 tick 调用 `input()`，内部取消按 `release()` 处理；终局松键同样处理。没有自行近似实现另一套规则。
- 辅助核验覆盖 5 个 v2 session、9 条轨道：**309 个轨道存储帧的身体、食物、分数、status、tick、结束原因全部相符；9 个最终完整游戏 state 均相符**。第 5 个 session 为人工结束，不能算自然死亡样本；4 条旧 custom-systemone 对照轨道没有有效输入，不把无动作结算归因于模型决策能力。
- 下述 4 条主轨道共核验 **152 个存储帧、80 个有 actionId 的 decision**。辅助总样本内 92 对已接受 decision/input 的 action、duration、appliedTick 全部一致；97 个主模型 decision 均满足 `observedTick >= 上次已接受输入的 appliedTick`。

## 时间字段的准确含义

- 全局模拟 60 tick/s；Snake 每 20 tick 移动一次，即 3 格/s。坐标左上角 `(0,0)`，x 向右、y 向下，范围 0..19。
- `observedTick`：请求捕获局面的模拟 tick。
- 表中 `returnTick`：**持久化 decision 事件的 tick，即结算时刻的会话 tick，并非独立记录的 HTTP 返回 tick**。凭证复核等工作发生在模型返回与结算之间，不能从旧记录拆分精确耗时。
- `appliedTick`：接受输入后的下一物理 tick。Snake 在随后第一个 20 的倍数移动 tick 才执行转向。因此它不等于「头部已经移动/方向已经改变」。
- `移动数`：观察后至结算期间实际成功位移数；撞墙尝试不使蛇头移出棋盘，额外失败尝试另列。
- 游戏结束后模拟 tick 冻结。最后一行的 returnTick 不能用来算完整响应延迟；附加 `settleWallTick` 是按无暂停局的 `event.at` 与模拟 anchor 换算出的墙钟等效 tick，仅说明结算已经晚于死亡，不是假装游戏继续运行。

## 分类判断与可验证边界

| 类别 | 审计判断 |
|---|---|
| 观察时就选择立即撞墙/身体的方向 | 4 主样本的 80 个选择均未出现。这里仅检查观察位置的下一格及合法腾出的尾格，不能据此称整个策略安全。 |
| 请求期间位置/目标改变，纠正动作迟到 | 已证实。4 个最后转向全部在死亡后结算；StartLux 的旧食物在请求期间被吃掉，Jev 样本 2 的同方向答案到达时头已经贴墙。 |
| `queued` 被模型误解 | **不可直接识别。** 4 主样本有 36 次观察的 queued 与 direction 不同，其中 35 次选了 queued 同方向；StartLux 是 18/17，三局 Jev 分别是 7/7、3/3、8/8。该重复模式值得对照实验，但也可能是有意继续该方向。未读取 thought，不能给模型编造解释。 |
| 状态表达存在混淆机会 | 源码事实：同一观察可能 direction=右、queued=上；当前观察明确写出 queued 下一移动生效，prompt 已写延迟及持续前进。不能说现有 prompt 完全没目标或没说明；可以检验更显著的展示是否改善行为。 |
| 动作映射/物理重放故障 | 当前样本未发现。92 对动作映射一致，309 帧与终态吻合。 |
| 上次输入未进入下一物理 tick 就启动下次观察 | 当前样本未发现，所有观察满足现有 gate。但 gate 只等一物理 tick，不等 Snake 下一次格移动，因此 queued 非空是正常现象，不能混称旧调度 bug。 |
| 调度保证回答永远适用当前空间位置 | 当前实现没有这种保证：检查会话/轨道仍运行及动作仍合法；Snake 并不因头部位置变化自动丢弃合法方向。这是实时规则语义，不是这次发现的回退或自动误操作。 |

本审计不能从最终动作推断模型的内部理由，也不能证明另一个 prompt 必然提升成绩；没有读取实际完整请求，版本标签及当前源码能核实生成协议，不能替代网络端逐字收包证明。真实网络到达、解码完成、凭证后检查各阶段也没有独立历史时间戳。这里用有限真实样本定位可检验假设，不作模型强弱排名。

## 为 A/B/C 实验提供的依据

- A 固定现有 v4。B 只调整 prompt，明确先推演**当前 direction 加已接受 queued**在响应窗口内的轨迹，判断转向何时必须到达；不要把 100 ms 当作仅移动一格，不把重复 queued 当作必需的确认。
- C 只重新组织模型可见的状态，并给所有现有候选同样字段的几何事实，例如下一步位置/是否立即碰撞/距墙格数。不要筛掉危险候选、替模型决定方向、泄露未来随机食物或改模拟/速度/返回时序。
- 当前真实证据更支持同时统计「距死亡剩余时间与实际响应耗时」「请求期间移动数」「食物是否在 pending 期间变化」「queued 不同于 direction 时的重复比例」，不能只看 food 总数下结论。
